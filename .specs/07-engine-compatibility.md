# 07 — Skillex 0.10 compatibility

The registry tooling pins `@atheory-ai/skillex` to **0.10.0**. The engine
contract is `internal/packs/pack.go` at that release, not a moving engine
checkout. Registry policy adds path-derived identity, publication metadata,
regular portable skill-file paths, and the content/security gate.

## Pack manifests

Supported top-level fields are `name`, `version`, `description`, `source`,
`detectors`, `skills`, `mcp-servers`, and `registry`. The engine rejects unknown
fields in its typed structures. `registry` is an explicitly supported open
metadata mapping; its license, authors, homepage, and compatibility data stay
inside the shipped `pack.yaml`. No separate `registry.yaml` is required.

A pack must contain at least one skill or MCP suggestion. Skill-only, MCP-only,
and mixed packs are supported. MCP entries require `ref`, an exact `version`,
`relationship: suggested`, and valid activation/scope. `capabilities.prefer`
contains nonempty capability names. Packs cannot supply executable commands,
transports, endpoints, environment variables, or credentials.

## Activation and scope

Leaf activation fields are alternatives: any matching `files-present`,
`files-matching`, `dependency-declared`, or `detector` activates the entry.
Use recursive `all` when every gate must match. An `all` list must be nonempty,
cannot coexist with leaf fields at the same level, and has a maximum nesting
depth of 32. Built-in detectors are docker, go, javascript, and typescript;
declare other detectors in the pack.

| Scope | File-backed activation | Activation without file evidence |
|---|---|---|
| omitted / subtree | Matching file's directory and descendants | Dependency boundary and descendants, or entire project |
| repo | Entire project | Entire project |
| directory | Matching file's immediate directory | Dependency boundary and descendants, or entire project |
| matching-files | Matching files; `files` can override the selected patterns | Dependency boundary and descendants, or entire project |
| nearest-ancestor | Matching file's directory and descendants | Dependency boundary and descendants, or entire project |
| boundary | Dependency boundary and descendants, or entire project | Same |

Dependency conditions compare declared facts, including exact version strings;
they do not resolve semver compatibility ranges. Dependency-shipped packs need
configured `Rules[].DependencyBoundary` entries in the consumer project.

MCP suggestions become discoverable only with project opt-in: configuration
Version 5, `MCP.Enabled: true`, and at least one `MCP.Bindings` entry. They
describe relevance without approving server execution. Without a trusted
transport they remain setup-required. Refresh leaves host MCP configuration
unchanged.

## Verification gates

- `npm test`: tooling, manifest parity, activation, and local pack query/read.
- `npm run test:contract`: released-CLI manifest/activation/local-pack fixtures;
  CI runs these on Linux, macOS, and Windows with Node 20.
- `npm run lint:packs`: registry policy plus manifest validation.
- `npm run validate`: repository skill test structure.
- `npm run test:published-pack`: an explicit network check against the canonical
  signed manifest and immutable example archive. CI runs it as a separate
  Linux job on pull requests, main pushes, or manual dispatch.

The live check verifies preview has no installation writes, installs the
example matching the committed manifest identity and digest, retains signed
evidence, and lists/refreshes/queries/reads with HTTP(S) requests directed to a
closed local proxy. It also confirms modified installed guidance is rejected.
A new example release requires updating the signed committed manifest through
the publication workflow; never edit that evidence to make a test pass.

Release CI runs tooling and engine contract tests before building the pack.
The committed signed manifest is not regenerated by these checks.

## Limits of the 0.10 consumer

The consumer installs the latest stable version by name using one registry and
the engine-bundled signing identity. It does not implement compatibility-range
resolution, federation/custom trust, or pack search/info/update/remove commands.
Offline refresh authenticates saved evidence and embedded revocations; it
cannot learn newly published revocations without a fresh manifest fetch.
Artifact attestations are produced by release CI, but 0.10's install consumer
authenticates the manifest and archive digest rather than verifying separate
GitHub provenance or tarball signature assets.
